# 결과: 새 기준 구성(값 7개)의 측정·학습·평가 C++ 이식 (11-12)

## 문제

11-12 에 정한 새 기준 구성은 Python 분석으로만 있었다. 팀 기준(C++17, MSVC v141, OpenCV 3.4.15)으로 옮겨 같은 숫자가 나오는지 확인해야 했다.

새 기준 구성: QR 536점 이동의 가로 평균 1 + 위·아래 바 기울기 2 + 나사 4개의 가로 이동(기울기 영상 맞춤) 4 = 값 7개. 절대 영점 라벨, 증강 없음, 00004 Huber 학습식.

## 방법

- 도구: `실험/v2tool/` (CMake, C++17, MSVC v141, OpenCV 3.4.15)
  - `src/screw_gradient.{hpp,cpp}`: 나사 기울기 영상 맞춤(새로 작성)
  - `src/huber_fit.{hpp,cpp}`: 00004 학습식을 값 개수와 무관하게 쓰도록 옮긴 것(새로 작성)
  - `src/main.cpp`: 측정(`measure`)과 평가(`eval`) 실행
  - 536점 추적은 `00000_final_Y_T control` 의 tracker, 바와 나사 초기 위치는 `00004_final_Y_T` 의 관측기 소스를 그대로 링크했다.
- 사진 702장(ID 702 제외, T=+2.00 12장 제외), 절대 영점 라벨, 분할은 20261112_1835 실험의 것(`결과/입력/splits.tsv`).
- 대조 기준: 같은 구성의 Python 분석값(`결과/입력/python_features7.tsv`)과 Python 평가 결과(20261112_1835 의 `가로만_결과.tsv`).
- 빌드와 실행(저장소 루트에서)
  - `cmake -S "<이 폴더>/실험/v2tool" -B .batch_build/v2tool -G "Visual Studio 18 2026" -A x64 -T v141 -DOpenCV_DIR="C:/opencv/build"` 후 `cmake --build .batch_build/v2tool --config Release`
  - `python "<이 폴더>/실험/prepare_inputs.py" .batch_build/v2run/in` (입력 표를 만든다. 자료 준비만 한다)
  - `v2tool measure experiments/hye/00004_final_Y_T/assets "experiments/hye/00000_final_Y_T control/assets" .batch_build/v2run/in/photos.tsv .batch_build/v2run/out`
  - `v2tool eval .batch_build/v2run/out/features7.tsv .batch_build/v2run/in/labels.tsv .batch_build/v2run/in/splits.tsv .batch_build/v2run/eval_cpp`
  - 인자 경로는 ASCII 로 준다. 702장 측정에 약 2분 걸렸다.

## 결과 3 — 이식 중 찾은 문제: warpAffine 의 계단 오차

처음에는 나사 맞춤에 `cv::findTransformECC` 를 그대로 썼다. 그 결과(`결과/cpp_warpAffine_사용판/`)는 Python 과 달랐다.

| | findTransformECC 사용 | 직접 보간으로 고친 것 |
|---|---:|---:|
| 나사 값의 Python 대비 RMS 차 | 0.011 px (최대 0.018) | 0.00001 px (최대 0.0002) |
| 주 검증 탈락 평균 | 0.50 | 0.10 |
| 50/50 탈락 평균 | 1.00 | 0.20 |
| 세션 통째로 빼기 | 98.2% | 98.8% |

- 차이는 평균 0, 표준편차 0.0107 px 로 ±0.018 px 안에 고르게 퍼져 있었다. OpenCV 3.4.15 의 `warpAffine` 이 좌표를 1/32 px 단위로 끊어 계산하기 때문으로 보인다(추정. OpenCV 5.0 에서는 이 차이가 없다).
- 나사 하나의 반복 흔들림이 0.012 px 인데 0.011 px 의 오차가 더해지면 기울기 영상 방식의 이점이 거의 없어진다.
- 그래서 `screw_gradient.cpp` 는 `findTransformECC` 와 같은 갱신식을 쓰되 영상 이동을 정확한 양선형 보간으로 직접 계산한다.
- 00004 의 QR 측정도 같은 `warpAffine`/`warpPerspective` 를 쓴다(`third_party/ecc_compat.cpp`). 같은 계단 오차가 QR 54값에 들어 있을 수 있다. 확인하지 않았다.

## 한계

- 값 교란 강건성 시험과 날 차이 증강은 C++ 로 옮기지 않았다. 새 기준 구성은 증강을 쓰지 않는다.
- 이 도구는 실험용 실행 파일이다. 공개 API(`alignment()`, `joint()`)와 `experiments/selected_modules.cmake` 에는 연결하지 않았다. 배포 모델(00004, 값 66개)은 그대로다.
- 536점 추적, 00004 의 QR·바 관측, 나사 초기 위치 측정을 모두 돌린다. 값 7개에 필요 없는 QR 54값 계산이 포함돼 있어 속도를 줄일 여지가 있다. 속도는 재지 않았다(702장 약 2분, 병렬).
- 세로 값을 Y, T 계산에서 뺐으므로 세로 이상을 잡는 품질 판정이 따로 필요하다. 만들지 않았다.
- 702장은 개발에 쓴 자료다. 실제 로봇 복귀 검증이 아니라 정지 사진 평가다.
