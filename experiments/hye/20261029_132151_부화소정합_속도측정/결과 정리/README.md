# 부화소 정합 방법 3단계: 속도 측정

작성: 2026-10-29. 상태: 개발 노트북에서 정해진 절차로 쟀다. 운용 장비에서는 다시 재야 한다.
공통 규칙은 [ALGORITHM_RULES.md](../../../../ALGORITHM_RULES.md)를 따른다. 측정 절차는 [재실험 방법론](../../20261029_121819_특징점_추적_재실험방법론/실험%20방법/PROTOCOL.md) 9절을 따랐다. 정합 방법은 [1단계](../../20261029_122323_부화소정합_합성정답/결과%20정리/README.md)의 9개, 모델은 [2단계](../../20261029_131112_부화소정합_YT결과영향/결과%20정리/README.md)의 전체 학습 모델이다.

## 절차

| 항목 | 내용 |
|---|---|
| 자료 | 20261014 Y 80 + T 200 = 280장 |
| 초기화 | 채택 측정기(`Tracker`) 생성, 비교용 9방법 전체 생성, 모델 읽기, center 측정을 각각 5회 |
| cold | 9방법 생성 직후 첫 사진의 첫 호출, 5회 |
| warm-up | 사진 10장 × 9방법 (기록 안 함) |
| 본 측정 | 280장 전체 5회 반복. 매 반복마다 사진 순서와 사진 안의 방법 순서를 고정 seed(20261029+반복 번호)로 섞음 |
| 스레드 | 주 측정은 OpenCV 1스레드. 기본 스레드(22)는 2회 반복으로 따로 측정 |
| 집계 | 사진별 반복 중앙값 → 280장의 중앙값 / p95 / 최대 |
| 단계 | 파일 읽기(BMP → 회색), 측정(방법별), P12 특징, 모델 추론 |

측정할 때는 사진의 kCrop 영역만 메모리에 두고 고정 캔버스에 붙여 넣었다. 모든 방법이 이 영역 안만 읽는다. 처음 3장 × 9방법에서 원본 영상과 결과 차이가 0인 것을 확인했다(`environment.json`의 `canvas_equivalence_max_diff`).

**환경:** Intel Core Ultra 9 185H(성능·효율 코어 혼합, 논리 22), 노트북 배터리 사용 중, 전원 구성표 "균형 조정", MSVC v141 Release, OpenCV 3.4.15. 편집기·브라우저·다른 에이전트가 함께 실행 중이었고, 실행 직전 전체 CPU 사용률은 약 13%였다. 스레드를 특정 코어에 고정하지 않았다. 그래서 절대값은 흔들릴 수 있다. 방법 사이의 비교는 순서를 섞어 같은 조건에 놓았다.

### control 전체 경로 (측정 + P12 + 추론, ms)

| 측정 | 영상이 메모리에 있을 때 중앙값 / p95 | BMP 파일 읽기 포함 중앙값 / p95 |
|---|---|---|
| GN(채택) | **43.0 / 56.8** | 223.4 / 256.7 |
| LK(1단) | 16.6 / 23.2 | 197.2 / 225.1 |
| ECC | 192.8 / 245.9 | 375.2 / 443.7 |

P12 특징과 모델 추론은 합쳐서 0.2 ms 아래다. 운용 API `alignment(cv::Mat&)`는 이미 메모리에 있는 영상을 받으므로 "메모리에 있을 때"가 해당한다. 개발 PC에서 24 MB BMP를 읽고 회색으로 바꾸는 데 180 ms(중앙값)가 들었다. 카메라에서 받는 경로의 시간은 따로 재야 한다.

### 초기화와 cold (1스레드, 5회 중앙값 ms)

| 항목 | 중앙값 | 최대 |
|---|---|---|
| 채택 측정기 생성(`Tracker`, center 측정 포함) | 425.7 | 442.8 |
| 2단계 모델 읽기 | 4.1~5.4 | 8.8 |
| GN 첫 호출(cold) | 65.4 | 111.3 |
| LK 첫 호출(cold) | 32.2 | 48.2 |

초기화는 프로그램 시작 때 한 번이다. cold 첫 호출은 이후 호출(warm)보다 1.5~2배 느렸다.

## 해석

- **채택 GN 경로는 영상이 메모리에 있을 때 장당 약 43 ms(p95 57 ms)다.** LK보다 26 ms 느리지만 2단계에서 축·부호 100%를 지킨 것은 GN뿐이었다. 이 차이를 줄이려고 측정기를 바꿀 근거는 없다. 2단계 흐름에서는 joint(1차) 쪽 시간이 더 크다는 기록도 있다([LK 재학습 실험](../../20261029_132047_control_LK측정_재학습/결과%20정리/README.md)).
- **ECC는 GN보다 4.5배 느리고 2단계 결과도 나빴다.** 후보에서 뺀다.
- **기본 스레드(22)는 대부분 방법을 오히려 느리게 했다(GN 43 → 65 ms).** 작은 창을 점마다 처리하는 일이라 스레드를 나누는 비용이 더 크고, 효율 코어에 배치될 수도 있다. 영상 전체를 다루는 피라미드 LK만 빨라졌다(14 → 8 ms). 운용 설정에서는 OpenCV 스레드 수를 명시적으로 정하고 측정하는 것이 좋다.
- **이 노트북의 결과는 참고값이다.** 앞선 실험의 1회 측정(GN 38~40 ms)과도 범위가 겹친다. 운용 장비에서 같은 도구로 다시 재야 한다.

## 빌드와 실행

저장소 루트 PowerShell. `results/`가 있으면 덮어쓰지 않고 멈춘다. 전체 실행은 약 25분이다.

```powershell
cmake -S "experiments/hye/20261029_132151_부화소정합_속도측정" -B build-subpixel-speed-20261029 -G "Visual Studio 18 2026" -A x64 -T v141 -DCMAKE_GENERATOR_INSTANCE="C:/Program Files (x86)/Microsoft Visual Studio/18/BuildTools" -DOpenCV_DIR="C:/opencv/build"
cmake --build build-subpixel-speed-20261029 --config Release
.\build-subpixel-speed-20261029\Release\subpixel_speed.exe
```

인자 `<결과 폴더> quick`은 사진 20장만 쓴다. 2단계 `results/models`의 `m0/m1/m2_full.json`을 읽는다.
