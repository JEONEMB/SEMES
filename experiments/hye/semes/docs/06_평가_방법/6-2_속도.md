# 6-2. 속도

"사진 한 장을 재는 데 얼마나 걸리나"를 어떻게 재고, 얼마나 나왔는지 정리했다.

도구: `tools/evaluate/measure_speed` (정상 사진), `tools/environment/measure_slow_cases` (느린 경우와 영점 잡기)

## 1. 측정 항목

속도는 **무엇을 포함했는지**에 따라 크게 달라진다. 그래서 나눠서 잰다.

| 재는 것 | 포함하는 것 |
|---|---|
| 측정만 | `measure_alignment` 를 부르고 결과가 돌아올 때까지. 사진은 이미 메모리에 있다 |
| 사진 읽기 | 파일에서 읽어 회색 사진으로 푸는 시간 (사진 한 장이 24 MB) |
| 읽기 + 측정 | 위 둘의 합 |
| 준비 | `initialize` 한 번 (프로그램을 시작할 때) |

실제 장비에서 카메라가 사진을 메모리로 바로 넘겨 주면 "측정만"이 해당하고, 파일로 저장했다가 읽으면 "읽기 + 측정"이 해당한다.

---

## 2. 측정 방법

| 조건 | 값 |
|---|---|
| 사진 | 받은 사진 715장 |
| 스레드 | OpenCV 스레드 1개일 때와 4개일 때를 따로 (`cv::setNumThreads`) |
| 빼는 것 | 스레드 설정마다 첫 1장 (처음 부를 때의 준비 시간이 섞여서) |
| 보고하는 값 | 가운뎃값, 95% 지점(100장 중 95번째로 느린 값), 최대 |
| 빌드 | Release |
| 컴퓨터 | 노트북, Intel 프로세서, 논리 코어 22개 |

**왜 가운뎃값만 보고하지 않나**: 평균이나 가운뎃값만 보면 가끔 느린 경우가 가려진다. 장비에서는 "가장 느릴 때"가 중요할 수 있어서 95% 지점과 최대를 같이 적는다.

## 3. 결과

| | 가운뎃값 | 95% 지점 | 최대 |
|---|---:|---:|---:|
| **측정만, 스레드 1개** | **27.2 ms** | 48.8 ms | 81.9 ms |
| **측정만, 스레드 4개** | **13.7 ms** | 30.0 ms | 61.2 ms |
| 사진 읽기 | 158 ~ 161 ms | 173 ~ 178 ms | 224 ~ 294 ms |
| 읽기 + 측정, 스레드 1개 | 180.5 ms | 201.5 ms | 327.2 ms |
| 읽기 + 측정, 스레드 4개 | 167.4 ms | 184.5 ms | 241.4 ms |
| 준비 (`initialize`) | 156.9 ms (한 번) | | |

- 측정 자체는 14 ~ 27 ms 다. 2026-11-16 나사 둘레 영역 맞춤을 넣으면서 늘었다 (넣기 전 스레드 1개 18.0 ~ 18.8 ms, 95% 지점 21.2 ~ 21.9 ms; 스레드 4개 9.5 ~ 9.8 ms, 95% 지점 11.3 ~ 11.9 ms. [9-11](../09_추가_논의/9-11_나사_둘레_영역_값_추가.md)). 위 측정만 두 줄은 이번에 다시 잰 값이고, 사진 읽기와 준비 줄은 이전에 잰 값이다. **파일에서 읽으면 읽는 시간(약 160 ms)이 대부분**을 차지한다.
- 스레드 4개가 1개의 약 2배 빠르다. QR 3개와 나사 4개를 동시에 찾기 때문이다. 스레드를 아주 많이(22개) 쓰면 나누는 비용 때문에 오히려 느려졌다. 4개 근처를 권한다.
- 2026-11-16 QR 탐색을 바꾼 뒤, 같은 컴퓨터에서 바꾸기 전과 이어서 다시 쟀다. 측정만: 스레드 1개 18.1 → 17.4 ms, 4개 8.8 → 9.5 ms (가운데값). 실행마다의 변동 수준이라 위 표는 그대로 둔다 ([9-8](../09_추가_논의/9-8_QR_띠_봉우리_탐색으로_전환.md) 5-2).
- 2026-11-16 QR 소수 위치 계산을 가우스 맞춤으로 바꾼 뒤, 바꾸기 전과 번갈아 두 번씩 쟀다. 측정만: 스레드 1개 19.8, 19.7 → 19.5, 19.0 ms, 4개 11.1, 10.4 → 11.4, 10.5 ms (가운데값). 차이는 실행마다의 변동 안이라 위 표는 그대로 둔다 ([9-10](../09_추가_논의/9-10_QR_소수위치_가우스맞춤으로_전환.md)).

### 3-2. 느려지는 경우

읽는 법

- **가장 느린 것은 화면이 흐린 경우다** (초점 흐림, 이동 흐림, 안개). 정상의 약 1.4 ~ 1.6배다. 흐리면 나사 다듬기를 더 여러 번 되풀이하기 때문이다. 잡음도 약 1.2 ~ 1.4배다.
- **가림과 실패는 정상보다 빠르다.** 나사가 없으면 그 나사의 다듬기를 건너뛰고, QR 을 못 찾으면 1단계에서 끝난다 (2 ~ 5 ms).
- 빛, 위치 이동, 회전, 컬러 입력은 정상의 0.9 ~ 1.2배로 거의 같다.
- 잰 것 중 한 장의 최대는 스레드 1개 74.5 ms, 스레드 4개 73.2 ms 다. 다만 정상 사진도 54.4 ms 가 나왔으므로, 최대는 상황보다 그 순간 컴퓨터 상태의 영향이 크다.
- 같은 측정을 한 번 더 돌렸을 때 스레드 1개의 정상 평균이 41.3 ms 로 올랐다 (컴퓨터의 다른 작업 영향). 그때도 배율은 같았다 (흐림 1.37 ~ 1.46배, 가림 0.75 ~ 0.90배). **ms 값보다 배율을 믿는 편이 맞다.**
- 경고와 실패가 나면 측정 함수가 알림 한 줄을 화면에 쓴다. 그 시간도 들어 있다.

영점 잡기 (`set_zero_from_photos`, 사진 읽기 제외, 5번 반복). 받은 사진에 명령 (0, 0) 사진이 없어 센터 사진을 복사해 같은 사진 여러 장으로 쟀다.

| 사진 수 | 스레드 | 평균 | 최소 | 최대 |
|---|---|---:|---:|---:|
| 5장 | 1개 | 155.6 ms | 147.9 ms | 167.6 ms |
| 5장 | 4개 | 147.1 ms | 139.8 ms | 152.8 ms |
| 10장 | 1개 | 271.8 ms | 249.1 ms | 287.2 ms |
| 10장 | 4개 | 281.7 ms | 260.0 ms | 304.8 ms |

사진 한 장을 더할 때마다 약 25 ms 가 든다. 스레드를 늘려도 줄지 않는다.

1단계의 위험한 경우(반사, 가림, 큰 이동, 세로 이동)만 따로 잰 값은 [5-1 QR](../05_구현_방법/5-1_QR.md) 2-6 에 있다 (1단계 최악 약 14 ms, 이전 방식은 108 ms).

## 4. 다시 재 보는 방법

```
build\Release\measure_speed.exe data/model data/new_photos/tables 결과폴더
build\Release\measure_slow_cases.exe data/model data/new_photos/tables 결과폴더2
```

- `결과폴더/speed_report.txt` 에 위 표가, `times.tsv` 에 사진마다의 시간이 나온다.
- 사진 수를 줄이려면 끝에 `--count 100` 을 붙인다.
- 사진 폴더를 직접 넘겨도 된다 (`data/new_photos/20261029`).
- `결과폴더2/slow_cases_report.txt` 에 3-2 의 표가 나온다. 상황마다 쓰는 사진 수는 `--count 20` 으로 바꾼다.

## 5. 한계

- 노트북 한 대에서 잰 값이다. 장비의 컴퓨터에서는 다르다. 장비에서 위 명령으로 다시 재야 한다.
- 다른 프로그램이 같이 돌면 달라진다. 같은 날 두 번 잰 정상 평균이 28.9 ms 와 41.3 ms 였다.
- 느린 경우는 합성 사진 20장씩으로 잰 값이다. 실제로 흐리거나 가려진 사진으로 잰 것이 아니고, 합성한 세기보다 더 심한 경우는 재지 않았다.
- 범위 밖 큰 자세(Y 2 mm 초과, T 1도 초과)의 실제 사진으로는 재지 않았다. 확인 안 함.
- 카메라 촬영, 사진 전송, 로봇 이동 시간은 들어 있지 않다.
