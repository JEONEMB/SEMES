# 1차 joint C++ 모듈 v2

공통 목표, 관측 제약, 평가는 [ALGORITHM_RULES.md](../../../ALGORITHM_RULES.md)를 따른다. 1차 joint의 판정 기준은 한 장 `|eT| ≤ 0.01`(T 1틱)이다.
v1 [00000_final_Y_T_joint](../00000_final_Y_T_joint/README.md)에서 **측정은 그대로 두고 모델만 바꿨다.** 공개 함수, CMake 대상 이름(`semes_joint`), `assets/` 구조는 같다. 빌드에 쓰려면 [selected_modules.cmake](../../selected_modules.cmake)의 `SEMES_JOINT_DIR`를 이 폴더로 바꾼다(이 작업에서는 바꾸지 않았다).

## 무엇을 바꿨나, 왜

| | v1 | v2 |
|---|---|---|
| 측정 | QR 3개 ECC 호모그래피 → 가상점 27개 dx/dy 54값, 위·아래 바 48블록 세로 이동 48값 | **같음** |
| 모델 입력 | 102값 + 상호작용 = 204차원 | **2개:** s = QR 27점 가로 이동 평균, d = 위 바 기울기 − 아래 바 기울기 |
| 모델 | 204차원 GLS (전방 1차, 축소 0.01) | `(y, t) = [1, s, d] · W`, W는 3×2 최소제곱 |
| 학습 자료 | 20261014 + 20261020 341장 | 20261014 + 20261020 + 20261029 중 \|T\| ≤ 1인 563장 |

바꾼 이유는 세 실험으로 확인했다.

1. **v1은 카메라 세로 이동에 약하다** ([A19](../20261104_093558_A19_QR선측정_안정성점검/결과/보고서.md)). 영상 전체를 세로로 0.25 px 옮기면 v1 T가 최대 0.017, 0.5 px면 0.033 움직인다. 날짜 사이 실제 카메라 세로 이동은 0.44 px였다. 바 블록 값 48개를 그대로 회귀에 넣어, 바 전체가 같이 오르내리는 성분을 T로 읽기 때문이다.
2. **바 기울기 차는 카메라 이동에 불변이다** ([A21](../20261104_094732_A21_바측정_강건화비교/결과/보고서.md)). 같은 교란에서 T 변화가 최대 0.0015다. 바 측정 방법 5가지(지금 블록 정합, Huber, 열 에지, 구간 ECC, 좁은 띠)를 비교했고, 지금 블록 정합이 실제 사진과 교란 모두에서 가장 좋아 측정은 바꾸지 않았다.
3. **2특징 모델이 학습하지 않은 날짜로 잘 넘어간다** ([A20](../20261104_093913_A20_실제joint측정_세션재영점/결과/보고서.md)). 20261014만으로 학습해도 20261029에서 233/234가 0.01 안이다. v1 구조(204차원)는 같은 조건에서 62/234였다.

joint의 Y 출력은 운용에서 쓰지 않는다(1차는 T만 적용). v2의 Y는 참고값이다.

## 함수 계약 (v1과 같음)

```cpp
void initialize_joint(const std::string& joint_assets);
Alignment_t joint(cv::Mat& src);
AlignmentDiagnostics alignment_diagnostics();
```

- 입력은 3840×2160, 8비트, 1/3/4채널 영상이다. 원본은 수정하지 않는다.
- 출력 `(y, t)`는 추정값이다. 이동 명령 변환, 단위 변환, 재촬영은 호출 측 책임이다.
- 측정 실패(QR NCC < 0.6, ECC 상관 < 0.8, 정밀화 10 px 초과, 바 블록 정합 실패)와 모델 파일 오류는 예외로 알린다. `(0, 0)`으로 숨기지 않는다.
- `outside_training_range`는 현재 사진의 s나 d가 학습 자료의 범위 밖이면 참이다. 값은 자르지 않는다. 575장 중 14장(T+2.00 12장 등)에서 참이었다.
- 초기화 때 모델 파일의 바 블록 중심과 `line_protocol.json`의 블록 중심이 다르면 예외를 낸다.

## 처리 흐름

1. `Observer::measure()`: QR별 NCC 대략 위치(±130 px, 못 찾으면 ±260, ±512) → ECC 호모그래피 → 가상점 27개 이동, 바 48블록 세로 이동 (v1과 같음)
2. `v2_features()`: s = 27점 가로 이동 평균. 바마다 24블록 이동을 블록 중심 x로 최소제곱 직선 적합해 기울기를 구하고 d = 위 − 아래
3. `JointModel::predict()`: `(y, t) = [1, s, d] · W`

## 검증 결과

이 맥(macOS, Apple clang, Homebrew OpenCV 5.0.0)에서 [tool/standalone](tool/standalone/CMakeLists.txt)으로 빌드해 돌렸다. 결과: [results/v2_validation_20261104](results/v2_validation_20261104/).

**v1과 같은 미사용 날짜 (20261014 + 20261020으로 학습 → 20261029 234장)**

|---|---|---|---|---|
| v1 (전달 모델, 같은 두 날짜로 학습) | 228/234 (97.4%) | 0.0039 | 0.0148 | 48/48, 최대 0.0087 |

|---|---|---|---|---|
| 전체 | 546/559 (97.7%) | 0.0036 | 0.045 | 195/201 (97.0%), 최대 0.020 |
| 1차 20261014 | 276/280 (98.6%) | 0.0036 | 0.012 | 118/120 (98.3%), 최대 0.012 |
| 2차 20261020 | 37/45 (82.2%) | 0.0069 | 0.045 | 29/33 (87.9%), 최대 0.020 |
| 3차 20261029 | 233/234 (99.6%) | 0.0029 | 0.016 | 48/48 (100%), 최대 0.008 |

나누는 방식을 바꾼 10가지 분할에서 전체 97.5~97.7%, 최대 0.045다. v1 구조(204차원)는 같은 분할에서 97.7~98.6%(A20)로, 모든 날짜를 학습에 넣으면 v1 구조가 조금 낫다.

**2차(20261020)가 낮은 이유.** 0.01을 넘은 8장은 모두 같은 자세 반복 3장 중 한 장이다.

| 자세 (Y, T) | eT (1), (2), (3) | 3장 평균 | QR 가로 이동 s (px) | 바 기울기 차 d |
|---|---|---|---|---|
| (0.5, 0.1) | +0.001, +0.005, **−0.020** | −0.005 | 14.28, 14.60, 14.41 | −0.387, −0.405, **−0.293** |
| (1.0, 0.1) | −0.005, +0.005, **−0.020** | −0.007 | 21.38, 21.69, 21.47 | −0.346, −0.392, **−0.280** |
| (0.1, 0.2) | +0.005, **+0.020**, **−0.020** | +0.002 | 16.31, 16.61, 16.42 | −0.848, −0.914, −0.736 |
| (0.1, 1.0) | +0.002, **+0.032**, +0.008 | +0.014 | 80.66, 81.00, 80.68 | −4.252, **−4.382**, −4.276 |
| (0.5, 1.0) | +0.008, **+0.038**, −0.002 | +0.015 | 86.70, 87.06, 86.76 | −4.264, **−4.397**, −4.218 |
| (1.0, 1.0) | **+0.010**, **+0.045**, +0.006 | +0.020 | 93.81, 94.14, 93.82 | −4.256, **−4.409**, −4.238 |

- 튄 사진은 QR 이동(s)과 바 기울기(d)가 **같은 방향으로 함께** 다른 두 장과 다르다. 서로 다른 구조물이 같은 답을 내므로 측정 오류가 아니라 그 사진에서 판이 실제로 다른 자세였을 가능성이 높다. 특히 2번째 사진은 모든 자세에서 s가 약 +0.3 px 크다(측정 잡음 0.01 px의 30배).
- 목표 근처(T = 0.1, 0.2) 실패 4장은 3장 평균이 모두 0.01 안이다.
- T = 1.0 혼합 자세는 3장 평균도 +0.014~+0.020으로 한쪽으로 치우친다. Y와 T가 함께 큰 자세는 2차의 한 사분면에만 있어, 선형 2특징 모델이 이 영역을 덜 맞춘다(학습 자료가 적은 영역의 계통 편향).
- 2차는 평가 사진이 45장뿐이라 한 장이 2.2%p다.

**공개 API 확인**: 575장에서 `joint()` 출력과 도구 계산의 차이 최대 1.1e-10. 측정 실패 0. 처리 시간 중앙 32 ms, p95 50 ms, 최대 84 ms (이 맥, 1스레드).

## 아직 0.01 밖인 사진

- 20261029: 1장 (Y+0.05 T+0.33 (3), 0.0164)
- 20261020: 대부분 Y와 T가 함께 큰 혼합 자세(T = 1.00)와 반복 중 한 장. 목표 근처(\|T\| ≤ 0.2)에서도 20261014만으로 학습하면 33장 중 4장이 0.02 수준으로 남는다(같은 자세 반복 중 한 장). 혼합 자세 학습 자료는 20261020 한 사분면뿐이다.
- 영상 잡음이 남은 약점이다. 실제 잡음 수준에서 1장 T 흔들림은 최대 약 0.003~0.004다. 같은 자리 3장 평균으로 줄일 수 있다(운용 선택).

## 학습과 재현

```bash
# 저장소 루트 CMake 없이 이 모듈과 도구만 빌드 (검증용)
cmake -S tool/standalone -B build_v2 -DCMAKE_BUILD_TYPE=Release
cmake --build build_v2 -j
T=build_v2/joint/joint_v2_tool
$T measure  assets ../../../data/clean assets/training_list.csv results/v2_validation_20261104/features.csv
$T fit      assets results/v2_validation_20261104/features.csv assets/joint_v2_model.json
$T evaluate results/v2_validation_20261104/features.csv results/v2_validation_20261104
$T check    assets ../../../data/clean results/v2_validation_20261104/features.csv results/v2_validation_20261104/check_public_api.csv
```

저장소 루트에서 빌드하면 `joint_v2_tool` 대상이 함께 생긴다. 팀 기준(Windows, MSVC v141, OpenCV 3.4.15) 빌드는 이 작업에서 확인하지 못했다. 코드는 OpenCV 3.4 API 범위로 썼고, 맥 빌드를 위해 SHA-256(Windows는 bcrypt, 그 밖은 CommonCrypto)과 `ecc_compat.cpp`의 `core_c.h`(OpenCV 5에서 없음)만 분기했다.

## 한계

- 575장 모두 개발에 노출된 자료다. 특징 구조(s, d)는 이 자료로 비교해 골랐다. 독립 날짜·실기 검증은 아니다.
- 정답은 파일명의 명령값이다. 반복 사진 사이에 판이 실제로 움직인 몫은 오차로 잡힌다.
- 20261029에는 자기 center 사진이 없다. v2는 center 재촬영 없이 쓰는 것을 전제로 평가했다.
