# 시뮬레이터 팀원 배포 — 문제점과 개선 (2026-11-03)

목적 : 하드웨어(로봇 스테이지)를 만드는 동안, 팀원 각자의 정렬 알고리즘이 **사진 → 추정 → 보정 이동** 반복에서
실제로 영점을 맞추는지 시뮬레이터로 먼저 검증한다. 이를 위해 시뮬레이터를 **exe 키트**로 배포하고,
팀원이 자기 파일을 넣어 바로 시험할 수 있게 만든다.

범위 메모 (사용자 결정)

- `dev` 브랜치 `legacy/KSH/Simulator` 는 머지 충돌 방지용 사본 → 이번 작업과 무관
- 로봇 구동(드라이버·펌웨어)은 별도 진행 → 시뮬레이터는 로봇을 **오차 모델**로만 흉내 냄
- 수정 대상은 `QR_Image/Simulator` (검증 후 사용자가 git 프로젝트로 옮기라고 지시할 때 옮김)

## 2. 개선 내용

### 2.1 실행 위치와 무관한 경로 (#1, #2, #3)

- **시뮬레이터 루트** = `config/simulator.yml` 이 있는 폴더. 실행하면 아래 순서로 찾아 그 폴더를 작업 폴더로 삼는다
  `--root` 인자 → 현재 작업 폴더 → exe 폴더 → exe 의 상위 폴더들 (각 폴더와 그 안의 `Simulator/` 를 확인)
  → exe 를 더블 클릭해도, VS 에서 실행해도, 다른 폴더에서 실행해도 같은 설정·데이터를 씀
- 설정의 경로는 **후보 목록** : 앞에서부터 처음 존재하는 것을 사용
  `data_dirs: ["data/img", "../QR_Image/img"]` (키트 구조 → 개발 폴더 구조)
- 데이터 폴더는 **하위 폴더까지** 탐색. 세트 = 경로의 `1st / 2nd / 3rd` 폴더 (없으면 파일 이름 규칙 — 평평한 폴더도 계속 지원)
- 폴더 이름의 라벨이 파일 이름보다 우선 (예 : `T+0.32` 폴더 안의 `T+0.33 (3)` 같은 오기)
- 사진 읽기는 파일을 바이트로 읽어 `cv::imdecode` → 한글 경로에서도 동작

### 2.2 빌드 (#4, #5)

- `Simulator/opencv.props` : OpenCV 위치 = 환경 변수 `OPENCV_DIR` (`…\build` 또는 `…\build\x64\vc15` 둘 다 인식) → 없으면 `C:\opencv\build`
- 툴셋 `$(DefaultPlatformToolset)` : 설치된 VS 버전(2019·2022·2026)의 툴셋을 자동 사용
- `Simulator/CMakeLists.txt` : 공용 코어 + 콘솔 앱 + 플러그인 SDK (팀 표준 CMake, Linux 에서도 빌드)

### 2.3 로봇 오차 = 실측 반복 정밀도 (#6)

| 항목 | 수정 전 | 수정 후 | 근거 |
|---|---|---|---|
| 반복 정밀도 Y σ | 2.0 µm (가정) | **7.53 µm** | 같은 지령 3장 97묶음(2차·3차, 자유도 194)의 흩어짐 7.55 µm 에서 추정 잡음 0.61 µm 를 뺀 로봇 몫 (95 % 구간 6.84 ~ 8.36) |
| 반복 정밀도 Θ σ | 0.001° (가정) | **0.00198°** | 같은 방법 (95 % 구간 0.00180 ~ 0.00220) |
| 이동 배율 오차 σ | 0.2 % (가정) | 0.2 % (가정 유지) | 따로 잰 자료 없음 — 측정되면 설정만 바꾸면 됨 |

출처 : `정렬 파라미터 실험계획` 보고서 단계 C (2026-11-01). 같은 보고서에서 실측 반복 정밀도로 200회 시험 시 성공 100 %, 이동 평균 1.52회.

### 2.4 추정기 끼우기 — 플러그인 DLL (#7, #8)

```
시뮬레이터 exe ──(C 함수 5개)── plugins/<이름>.dll ── 팀원 코드 (팀 공통 alignment())
```

- 시뮬레이터 안에 **추정기 인터페이스** `sim::Estimator` 를 두고 두 가지 구현을 둠
  - `ksh` : 내장 (Alignment 모듈, ROI 표시 등 진단 정보 포함)
  - `plugin` : DLL 을 실행 중에 읽음 (`LoadLibrary` / `dlopen`)
- 경계는 **C 함수**(`sdk/sim_plugin.h`) : 컴파일러·STL 차이와 `alignment()` 이름 충돌이 없음
- 팀원은 `sdk/team/<이름>/` 에 자기 `include/`, `src/` 를 그대로 넣고 `build_plugin.bat` → `plugins/<이름>.dll`
  - 래퍼(`sdk/team_alignment_plugin.cpp`)가 팀 공통 `Alignment_t alignment(cv::Mat&)` 를 부름 → 코드 수정 없이 연결
  - 초기화·기준 사진 교체 함수가 따로 있으면 `sim_hooks.cpp` 하나만 추가 (예시 `sdk/examples/ksh/`)
- 추정기는 설정(`estimator:`), 콘솔 인자(`--estimator`), MFC 화면의 **추정기 선택 상자**에서 고름

### 2.5 배포 키트 (#8, #9)

`build_kit.bat` 한 번 → `dist/SimulatorKit/` (압축해서 전달)

```
SimulatorKit/
├─ SimulatorMFC.exe        화면 앱
├─ Simulator.exe           콘솔 앱 (일괄 시험·결과 파일)
├─ opencv_world3415.dll, VC++ 실행 DLL (VS 없는 PC 에서도 실행)
├─ config/                 simulator.yml, alignment.yml, model_*.yml
├─ world/                  만들어 둔 가상 장면 → 데이터 없이도 바로 시험 가능
├─ data/img/               ← 팀 공통 데이터(1st, 2nd, 3rd)를 그대로 복사 (합성 검증·장면 다시 만들기 때만 필요)
├─ plugins/                ← 팀원 추정기 DLL
├─ sdk/                    플러그인 만드는 도구
└─ results/                실행 결과
```

- 팀원 모두 같은 데이터를 받았으므로 가상 장면을 미리 만들어 넣어도 조건이 같음

### 2.6 직선 모서리 실측 — 합성 사진 충실도 (점검 중 발견, #11)

팀원 알고리즘을 넣어 보니 **합성 사진에서 Θ 가 거꾸로 읽히는** 문제가 있었다 (이혜원 joint : 실제 사진 T+0.50 → +0.502°, 합성 사진 → −0.081°).

- 원인 : 이혜원 알고리즘은 QR 과 **벽 구조의 긴 가로선**(y ≈ 710, 1790 px)을 쓴다. 가로선은 2차원 정합이 안 되는 곳(조리개 문제)이라
  운동장이 이웃 값으로 채워져 있었고, 그래서 Θ 에서 선의 위아래 이동이 실제와 달랐다. ksh(QR + 문 홀)는 영향 없음
- 수정 : 질감은 없지만 한 방향 기울기가 강한 창(직선 모서리)은 **선에 수직인 성분만 1차원으로** 잰다
  (평균 단면 정규화 상관 → 포물선 → Gauss–Newton). 채택은 상관 ≥ 0.7, 맞춤 잔차 ≤ 0.15 px 로 거름
- 결과 : 직선 모서리 창 후보 161개 중 132개를 실측으로 넣음 (가상 장면 다시 만듦, 약 2.5분)

| 이혜원 joint, T+0.50 사진 | Y | Θ |
|---|---|---|
| 실제 사진 | +0.0003 mm | +0.5017° |
| 합성 (수정 전) | +3.0641 mm | −0.0809° |
| 합성 (수정 후) | +0.0263 mm | +0.4967° |

### 2.8 영점 맞춤 (2026-11-03 추가)

자체 기준 사진을 쓰는 추정기는 시뮬레이터와 영점이 다를 수 있다. 예 : 신윤석 qrwithbar 추정기는 2차 `center1` 을 기준으로 학습되어,
시뮬레이터(1차 `center` 영점)에서 Θ 가 늘 약 +0.032° 치우쳐 읽혔고, 자기 영점에 도착해 멈췄지만 참 오차 Y −91 µm, Θ −0.031° 로 실패했다.

- 시험을 시작할 때(기준 사진 등록 직후) 참 자세 (0, 0) 사진(새 촬영 잡음)을 한 번 추정 → 그 값을 영점 차이로 저장 → 이후 추정값에서 뺌
- 실제 장비에서 center 를 다시 찍어 영점을 잡는 절차와 같다
- 설정 `estimator.zero_calibration` : 0 = 안 함, 1 = 항상, **2 = 자동 (기준 사진 교체를 지원하지 않는 추정기만, 기본값)**
  → ksh(내장)·이승재(교체 지원)는 지금과 같고, 신윤석·이혜원 joint(교체 미지원)에만 적용
- 기록 : `trial.csv` 에 `raw_est_*`(추정기 원래 값), `zero_*`(영점 차이) 열 추가. 화면 수치 패널·다회 시험 요약에 영점 차이 표시
- 확인 (Linux, 이혜원 joint) : 영점 차이 Y +28.1 µm, Θ −0.0012° 를 빼고 시작 (−1.311 mm, −0.427°) → 4회 이동 후 참 오차 Y +29 µm, Θ −0.0004° 로 성공

### 2.9 영점 사진 바꾸기 (2026-11-03 추가)

참 자세 (0, 0) 으로 볼 사진을 고를 수 있다 (예 1차 `center` → 2차 `center1`).

- MFC : 윗줄 **[영점 사진]** 상자에서 고름 → 확인 → 가상 장면을 그 사진 기준으로 다시 만듦 (약 2~4분, 사진 데이터 필요)
- 콘솔 : `Simulator.exe --reference-photo center1` (설정 저장 + 장면 다시 만들기)
- 설정 : `paths.reference_photo` (상자에서 고르면 이 줄만 자동으로 고쳐 저장, 주석 유지)
- 이전 장면은 지우지 않고 `world\_backup\날짜\` 에 복사해 둠 (배포 키트에는 넣지 않음)
- 방법 : 운동장은 1차 사진(지령 좌표)으로 맞추고, 영점 사진의 자세 δ 를 운동장 상수항으로부터 최소제곱으로 구함
  (영점 사진에서 이동 = 0 → aY·δY + bT·δΘ + qT·δΘ² = −c). 합성은 참 자세 + δ 로 그려 참 (0, 0) = 영점 사진.
  1차 `center` 는 정의상 δ = 0 → 기존 결과와 같음. 합성 검증은 라벨(1차 지령 좌표)에서 δ 를 빼고 그린 뒤 다시 더해 비교
- 확인 (Linux) : `center1` → δ = Y −70.0 µm, Θ +0.0136° (1차 지령 좌표). 내장 ksh 다회 시험 10회 성공 10,
  멈춘 뒤 Y RMS 35.4 µm (center 영점 16 µm — ksh 모델 상수항이 1차 center 에 맞춰져 있어 차이), Θ RMS 0.0014°
- 주의 : 2차 사진을 영점으로 하면 파노라마 가운데(2차)와 운동장 학습 사진(1차)의 촬영일이 섞인다. 선을 쓰는 추정기(이혜원 joint)는
  이 조합에서 합성 오차가 커져 실패한 예가 있음 → 먼저 [합성 검증] 으로 확인

### 2.10 한 번 최대 이동 = 장비 제원 · 화면 윗부분 2줄 (2026-11-03 추가)

- 한 번 최대 이동을 장비 제원으로 맞춤 : Y 2 mm, **Θ 1°** (이전 Θ 2° 는 과제 문구 기준 가정값). 보정 명령이 더 크면 잘라서 여러 번에 나눠 이동
- MFC 윗줄이 길어 [추정기] 상자가 잘리던 문제 → 2줄로 나눔
  - 1줄 (시험 조작) : 시작 Y·Θ, [무작위 시작], [시작 위치로] | [1 단계], [자동 실행], [정지] | [다회 시험], 횟수
  - 2줄 (설정·도구) : [추정기] (넓게), [영점 사진] | [합성 검증], [파노라마 생성], [결과 폴더]

## 3. 검증 결과

### 3.1 빌드 (Windows, Visual Studio 2026 v145 · OpenCV 3.4.15)

- `build_kit.bat` 한 번으로 Simulator.exe, SimulatorMFC.exe, 예시 플러그인 ksh_plugin.dll 빌드 → `dist\SimulatorKit` (66 MB) + zip (27 MB) — 오류·경고 0
- 키트 자가 점검 : 다른 폴더에서 실행해도 루트를 찾음 (`시뮬레이터 루트 : …\dist\SimulatorKit`), 플러그인 목록 1개
- Linux (OpenCV 4.6, CMake) 에서도 코어·콘솔·플러그인 빌드 확인

### 3.2 키트 실행 (Windows, 데이터 없이 world 만으로)

| 시험 | 결과 |
|---|---|
| `--monte 30` (내장 ksh) | 성공 30/30, 이동 평균 1.67 · 최대 3회, 멈춘 뒤 Y RMS 16.4 µm (최대 30.9), Θ RMS 0.0016° (최대 0.0029), 한 단계 158 ms |
| `--monte 30 --estimator ksh_plugin` | **내장과 완전히 같음** (같은 seed) → 플러그인 경로가 결과를 바꾸지 않음 |
| `--run 1.5 -0.8` | 2회 이동 후 멈춤, 참 오차 Y −4.3 µm, Θ +0.0002° |
| MFC 화면 | 12 pt 글자, 버튼 폭 자동, [추정기] 상자에서 ksh ↔ 플러그인 전환 후 [1 단계]·[자동 실행] 정상 |

허용 범위는 프로젝트 기본(과제의 절반) Y ±45 µm, Θ ±0.005°.

### 3.3 팀원 알고리즘 연결 — 이혜원 joint (`feature/hye/experiments-pa-pt`, Linux 확인)

팀원 코드는 고치지 않고 `include\`, `src\`, `third_party\`, `assets\` + 연결 파일(`examples/joint_style`)만으로 플러그인 빌드·실행.

같은 라벨의 실제 사진과 합성 사진 39장 비교 (1차 Θ·Y 각 10장, 2차 19조합 각 1장)

| 묶음 | ksh 실제 → 합성 (Y RMS / Θ RMS) | 이혜원 실제 → 합성 (Y RMS / Θ RMS) |
|---|---|---|
| 1차 Θ 스윕 | 10.2 → 11.2 µm / 0.0033 → 0.0027° | 20.2 → 77.7 µm / 0.0036 → 0.0161° |
| 1차 Y 스윕 | 19.0 → 18.6 µm / 0.0013 → 0.0009° | 21.1 → 39.0 µm / 0.0044 → 0.0082° |
| 2차 Θ < 1° | 9.9 → 17.7 µm / 0.0021 → 0.0007° | 12.2 → 37.1 µm / 0.0019 → 0.0069° |
| 2차 Θ ≥ 1° | 48.6 → 37.8 µm / 0.0140 → 0.0119° | 25.8 → 271 µm / 0.0047 → 0.0720° |

- ksh : 합성 사진이 실제 사진과 같은 수준 → 시뮬레이터 결과를 그대로 믿을 수 있음
- 이혜원 joint : 수정 후 부호·크기는 맞지만 합성 사진 오차가 실제의 2~4배 → **시뮬레이터 결과가 실제보다 나쁘게(보수적으로) 나옴**
  - 다회 시험 20회 : 멈춘 뒤 Y RMS 32.1 µm (최대 53.2), Θ RMS 0.0062° (최대 0.0090) — 과제 허용(±90 µm, ±0.01°) 20/20, 프로젝트 기본(절반) 7/20
  - Θ ≥ 1° 는 가상 장면을 만든 사진 범위(±1°) 끝·밖이라 차이가 큼
- 결론 : **팀원은 먼저 [합성 검증]으로 자기 알고리즘의 '합성 − 실제' 차이를 확인**하고, 차이가 크면 시뮬레이터 수치를 상한(최악) 추정으로 읽을 것
