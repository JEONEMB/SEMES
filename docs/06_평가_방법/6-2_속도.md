# 6-2. 속도

"사진 한 장을 재는 데 얼마나 걸리나"를 어떻게 재고, 얼마나 나왔는지 정리했다.

도구: `tools/evaluate/measure_speed`

---

## 1. 측정 항목

속도는 **무엇을 포함했는지**에 따라 크게 달라진다. 그래서 나눠서 잰다.

| 재는 것 | 포함하는 것 |
|---|---|
| 측정만 | `measure_alignment` 를 부르고 결과가 돌아올 때까지. 사진은 이미 메모리에 있다 |
| 사진 읽기 | 파일에서 읽어 회색 사진으로 푸는 시간 (사진 한 장이 24 MB) |
| 읽기 + 측정 | 위 둘의 합 |
| 준비 | `initialize` 한 번 (프로그램을 시작할 때) |

실제 장비에서 카메라가 사진을 메모리로 바로 넘겨 주면 "측정만"이 해당하고, 파일로 저장했다가 읽으면 "읽기 + 측정"이 해당한다.

---

## 2. 측정 방법

| 조건 | 값 |
|---|---|
| 사진 | 받은 사진 715장 |
| 스레드 | OpenCV 스레드 1개일 때와 4개일 때를 따로 (`cv::setNumThreads`) |
| 빼는 것 | 스레드 설정마다 첫 1장 (처음 부를 때의 준비 시간이 섞여서) |
| 보고하는 값 | 가운뎃값, 95% 지점(100장 중 95번째로 느린 값), 최대 |
| 빌드 | Release |
| 컴퓨터 | 노트북, Intel 프로세서, 논리 코어 22개 |

**왜 가운뎃값만 보고하지 않나**: 평균이나 가운뎃값만 보면 가끔 느린 경우가 가려진다. 장비에서는 "가장 느릴 때"가 중요할 수 있어서 95% 지점과 최대를 같이 적는다.

---

## 3. 결과

| | 가운뎃값 | 95% 지점 | 최대 |
|---|---:|---:|---:|
| **측정만, 스레드 1개** | **19.2 ms** | 24.7 ms | 71.1 ms |
| **측정만, 스레드 4개** | **9.6 ms** | 12.9 ms | 61.4 ms |
| 사진 읽기 | 158 ~ 161 ms | 173 ~ 178 ms | 224 ~ 294 ms |
| 읽기 + 측정, 스레드 1개 | 180.5 ms | 201.5 ms | 327.2 ms |
| 읽기 + 측정, 스레드 4개 | 167.4 ms | 184.5 ms | 241.4 ms |
| 준비 (`initialize`) | 156.9 ms (한 번) | | |

- 측정 자체는 10 ~ 20 ms 다. **파일에서 읽으면 읽는 시간(약 160 ms)이 대부분**을 차지한다.
- 스레드 4개가 1개의 약 2배 빠르다. QR 3개와 나사 4개를 동시에 찾기 때문이다. 스레드를 아주 많이(22개) 쓰면 나누는 비용 때문에 오히려 느려졌다. 4개 근처를 권한다.
- 2026-11-16 QR 탐색을 바꾼 뒤, 같은 컴퓨터에서 바꾸기 전과 이어서 다시 쟀다. 측정만: 스레드 1개 18.1 → 17.4 ms, 4개 8.8 → 9.5 ms (가운데값). 실행마다의 변동 수준이라 위 표는 그대로 둔다 ([9-8](../09_추가_논의/9-8_QR_띠_봉우리_탐색으로_전환.md) 5-2).

### 3-1. 단계별 시간 (개발 중에 잰 값)

| 단계 | 시간 | 비고 |
|---|---|---|
| QR 찾기 | 약 5 ms | 점 536개를 추적하는 방식은 약 23 ms 였다 |
| 나사 대략 찾기 | 5.7 ms | 넓게만 찾던 방식은 32.8 ms 였다 |
| 나사 테두리 맞춤 | 6.7 ms | |

### 3-2. 느려지는 경우

| 상황 | 이유 | 얼마나 |
|---|---|---|
| QR 이 크게 움직임, QR 하나가 가려지거나 반사됨 | 느려지지 않는다. QR 띠를 한 번만 훑는다 (2026-11-16 부터) | 1단계 최악 약 14 ms (스레드 1개). 이전 방식은 창을 넓혀 다시 찾느라 최악 108 ms |
| 나사가 가려짐 | 나사를 넓게 다시 찾고, 다듬기를 한도까지 되풀이한다 | 재지 않았다 |

1단계의 위험한 경우(반사, 가림, 큰 이동, 세로 이동)는 합성 사진 60장씩으로 1단계 시간만 쟀다 ([5-1 QR](../05_구현_방법/5-1_QR.md) 2-6). **나사가 가려진 경우와 측정 전체의 최악 시간은 재지 않았다.** 표의 "최대"(61 ~ 71 ms)는 정상 사진 중 가장 느린 값이다.

---

## 4. 다시 재 보는 방법

```
build\Release\measure_speed.exe data/model data/new_photos/tables 결과폴더
```

- `결과폴더/speed_report.txt` 에 위 표가, `times.tsv` 에 사진마다의 시간이 나온다.
- 사진 수를 줄이려면 끝에 `--count 100` 을 붙인다.
- 사진 폴더를 직접 넘겨도 된다 (`data/new_photos/20261029`).

---

## 5. 한계

- 노트북 한 대에서 잰 값이다. 장비의 컴퓨터에서는 다르다. 장비에서 위 명령으로 다시 재야 한다.
- 다른 프로그램이 같이 돌면 달라진다.
- 가려진 나사의 시간, 위험한 경우의 측정 전체 시간은 재지 않았다.
- 영점 잡기(사진 5 ~ 10장 평균 + 측정 한 번)의 시간은 재지 않았다. 하루 한 번 하는 일이다.
- 카메라 촬영, 사진 전송, 로봇 이동 시간은 들어 있지 않다.
