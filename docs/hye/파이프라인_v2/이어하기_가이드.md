## 4. 이어하는 방법

### 방법 A: 워크플로로 한 번에 (Claude Code)

에이전트에게 이렇게 말한다.

> docs/hye/파이프라인_v2/이어하기_가이드.md 를 읽고 4절 방법 A대로 워크플로를 이어서 돌려줘.

에이전트가 할 일
1. 1절대로 받고 `data/clean/`이 있는지 확인한다. 없으면 멈추고 알린다.
2. 이 컴퓨터에서 OpenCV C++ 빌드가 되는지 작은 예제로 확인하고, 빌드 명령 한 줄을 정한다.
3. Workflow 도구에 `scriptPath: docs/hye/파이프라인_v2/_워크플로/이어하기.js`(절대 경로로), `args: {"repo": "<저장소 절대 경로>", "build": "<2에서 정한 빌드 명령 설명>"}`을 넘겨 실행한다.
   - 스크립트는 `_워크플로/선정/<단계>.json`의 선정 목록을 읽고, 번역.md와 요약.md가 이미 있는 문헌은 건너뛴다.
   - 단계 페이지, 계획, 결과 파일이 이미 다 갖춰져 있으면 확인만 하고 넘어간다.
   - 순서: 남은 문헌 → 00_단계.md → 01_실험계획.md → 실험과 02_실험결과.md → v3 설계와 검토 → v3 구현과 검증 → 적대적 검증, 수정 → 결과보고.md
4. 매시 한 번 진행 상태를 점검한다(저널 갱신 시각, 사용 한도나 API 오류). 사용 한도로 멈추면 리셋 뒤 `resumeFromRunId`로 재개한다. 점검 때마다 plan.md 진행 기록에 한 줄 적는다.

[_워크플로/원래_전체.js](_워크플로/원래_전체.js)는 처음 실행한 원본 스크립트(조사 단계 포함)로, 참고용이다.

### 방법 B: 단계별로 손으로

워크플로를 쓰지 않으면 단계 하나씩 같은 순서로 한다. 지시문은 `이어하기.js`의 각 `agent()` 프롬프트를 그대로 쓴다. 남은 단계는 5절 집계로 찾는다.

저장소 최상위에서 아래를 돌리면 단계별로 무엇이 비었는지 나온다.

```
cd docs/hye/파이프라인_v2/단계
for d in */ */*/ */*/*/; do
  [ -f "$d/조사방법론.md" ] || continue
  n=$(find "$d" -name 요약.md | wc -l)
  echo "$d 요약=$n 단계=$([ -f $d/00_단계.md ] && echo O || echo X) 계획=$([ -f $d/01_실험계획.md ] && echo O || echo X) 결과=$([ -f $d/02_실험결과.md ] && echo O || echo X)"
done
```

## 6. 지킬 것

- 커밋과 push는 메인 에이전트만 한다. `feature/hye/pipeline-v2`에만 올린다. `git add .` 금지, 경로를 골라 stage한다.
- 올리지 않는 것: `data/`, 빌드 폴더, 캐시, 저장소 최상위의 `1` 같은 실수 파일
- 커밋 메시지와 문서에 사람 이름이나 "누가 무엇을 참고했다"는 표기를 넣지 않는다(문헌 서지의 저자명은 예외).
- 같은 폴더를 두 컴퓨터, 두 세션이 동시에 고치지 않는다. 한쪽을 멈추고 push한 뒤 다른 쪽에서 pull해서 시작한다.
- 확인하지 못한 서지와 수치를 지어내지 않는다. 봇 차단을 우회하지 않는다.
- 결과는 개발에 이미 노출된 자료의 성적임을 적고, 실기 검증을 주장하지 않는다.
